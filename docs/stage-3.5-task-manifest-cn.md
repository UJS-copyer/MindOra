# Stage 3.5 阶段文档：会话历史与多轮对话记忆（Chat History & Memory）

> 一句话用途：记录 Stage 3.5 登录用户多轮对话滑动记忆与会话持久化的 Spec 设计目标与实现交付情况。  
> 维护日期：2026-10-17　状态：**后端已交付，前台 UI 回退，管理端转入 3.6**

---

## 1. Spec 设计目标

Stage 3.4 实现了单轮问答的流式交互，但用户无法基于上一轮的讨论继续追问。本阶段旨在为已登录用户提供连贯的多轮对话体验与历史会话管理能力：

1. **上下文滑动窗口记忆**：多轮对话时自动携带历史上下文，采用滑动窗口机制（默认保留最近 4 轮问答，Token 总量硬限制在 3000 以内），保证模型能理解代词与连贯提问，同时不超出上下文上限。
2. **剥离历史引用编号**：在将历史助手的回答塞给本轮模型作为上下文时，自动剔除历史回答中的 `[1]`、`[2]` 等引用标记，防止历史引用干扰本轮检索切片的严格比对校验。
3. **会话与消息持久化存储**：在 MySQL 中新建会话表（`chat_conversation`）和消息表（`chat_message`），支持首问自动生成会话标题、多轮消息增量落库与会话删除。
4. **会话安全隔离**：用户只能查看和操作属于自己的对话历史；访客匿名请求不落库，携带不存在或非法的会话 ID 时按全新会话处理，绝不报错或泄露他人数据。

---

## 2. 实现情况

本阶段后端核心能力已全部交付并通过 API 实机验证；前台交互经过真实评审后进行了方案调整：

1. **后端会话引擎交付**：通过 Flyway V8 迁移脚本完成数据表建立，实现滑动窗口组装器与会话管理服务；单测与 API 真实链路实测通过（注册/登录 → 发起首问自动生成会话 → 连续追问上下文正确拼接 → 会话删除成功）。
2. **前台方案决策（半回退）**：在前台前台站（`apps/site`）初步实现了登录弹窗与会话列表，但在实机交互评审中发现：公开前台站加入厚重的用户登录与复杂抽屉会话后体验冗杂，不符合个人博客站“轻量、免登录、快速开箱即问”的定位。
3. **架构收口与路径调整**：决定采取**半回退策略**——后端会话引擎、数据表与接口完整保留；公开前台站保持 Stage 3.4 已验收的免登录极简形态；自用的多轮会话管理与全库问答需求转入 **Stage 3.6** 在管理端后台（`apps/admin-art`）集中建设。

---

## 3. 核心功能与接口一览

- **公开问答会话透传**：`POST /api/v1/public/rag/answer` 及 `/stream`，请求体支持传入可选的 `conversationId`；首次创建会话时由服务端在终态事件中回传生成的会话 ID。
- **获取我的会话列表**：`GET /api/v1/rag/conversations`（3.6b 起；原公开路径已删除），查询当前登录用户的所有未删除会话。
- **获取会话完整消息**：`GET /api/v1/rag/conversations/{id}/messages`，加载指定会话的历史问答。
- **删除指定会话**：`DELETE /api/v1/rag/conversations/{id}`，软删除指定的对话历史。

---

## 4. 关键规则与已知限制

- **历史消息中的拒答处理**：若上一轮助手回答为拒答，提示词中明确加入约束，要求模型“即便历史轮次未能回答，本轮若有新材料仍独立作答”，避免历史拒答诱导模型过度保守。
- **下一步衔接**：本阶段交付的会话引擎（V8 表、记忆装配、会话 CRUD）不重复开发；Stage 3.6b 会把它接入管理端问答（记忆 + 落库 + `persist`），并将会话 CRUD 收归用户域。会话历史的最终归宿是**账号**，公开站登录后复用同一套（暂记 4.7）；管理端不做聊天界面。
