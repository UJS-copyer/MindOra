## 一、目标与成功标准

**最小功能闭环**：用户发一个问题 → 系统返回答案 + 可定位到原文的引用（`chunkId` + `headingPath` + 源路径 + 文章 slug）→ 知识库无相关内容时明确拒答。

**两条硬性要求**：

1. **召回率尽量高**：默认启用已实测有效的**检索后扩展**（邻居 ±1 + 同章节 ≤4 条、每次查询新增 ≤1500 字符，实测 SpanHit@8 88.1% → 91.6%，优于单纯提高 k）。
2. **框架可扩展**：今天写单次问答，但**端口、上下文策略、请求/响应契约**都要为后续（SSE 流式、多轮对话、公开端点 + 限流、上下文策略开关）预留扩展位，不允许把最小实现写死。

**验收**：对 10 条负例全部拒答；对 5 条正例的引用能定位到原文；模拟 LLM 不可用时返回降级而非 500；`mindora-rag` 模块单测全过、全量 `mvn test` BUILD SUCCESS。

## 三、框架设计（为后续扩展预留的缝）

这是「考虑后续继续实现」的核心——**先把抽象定对，今天的最小实现只是这些抽象的第一个实现**。

```
mindora-rag
├── api/web                    RagAdminController          （今天：admin 调试端点）
│                                                          （后续：PublicRagController + 限流）
├── application
│   ├── RagAnswerService                                （编排：检索→组装→LLM→校验→产出）
│   ├── ContextAssembler                                （上下文组装 + 扩展 + 预算截断）
│   ├── AnswerCitationValidator                         （引用确定性校验 = 拒答的第三层）
│   └── port/RagAdapters
│         ├── ChatClientPort     chat(List<ChatMessage>, ChatOptions) → ChatReply
│         │                      ↑ 今天的最小实现是同步调用；ChatOptions 预留
│         │                        streaming: StreamCallback（默认 null，将来 SSE 启用）
│         ├── RetrievalFacadePort  search(RetrievalQuery) → RetrievalOutcome
│         │                      chunksOf(documentIds) → Map<chunkId, KnowledgeChunk>
│         │                      ↑ 对 mindora-knowledge 的最小化封装（将来若换检索实现，rag 不改）
│         └── (将来) ConversationMemoryPort               （多轮记忆，今天不实现，只在契约留 conversationId）
├── domain                   ChatMessage / ChatReply / RagAnswerRequest / RagAnswerOutcome /
│                            ContextPolicy（budget/expansionOn/sectionCap/maxPerDoc）/
│                            Citation / RefusalReason（枚举）
└── infrastructure/adapter   OpenAiCompatibleChatAdapter   （今天唯一 LLM 实现）
                             KnowledgeRetrievalFacadeAdapter
```

**为什么这样切**：

- `RetrievalFacadePort` 把「调 knowledge」收敛成一个窄端口，将来换检索引擎 / 加缓存 / 加查询改写时 `RagAnswerService` 不动。
- `ChatClientPort` 的 `ChatOptions` 带 `stream` 回调槽（今天传 null），将来接 SSE 只改 `RagAdminController` 的 wiring，不改服务逻辑。
- `ContextPolicy` 是 record，扩展（邻居/同章节开关、预算、每文档上限）都是新字段带默认值，老调用不受影响。

## 四、组件实现（按小提交拆分，每步可测）

### 提交 1：端口与领域模型 + LLM 适配器

- `RagAdapters.java`：`ChatClientPort`、`RetrievalFacadePort`、`ChatMessage(role,content)`、`ChatOptions(model,temperature,maxTokens,stream)`、`ChatReply(content, model, finishReason)`
- `domain/RagDomain.java`：`ContextPolicy`、`Citation`、`RagAnswerRequest`、`RagAnswerOutcome`、`RefusalReason{NO_CONTEXT, INVALID_CITATION, LLM_UNAVAILABLE}`
- `infrastructure/adapter/OpenAiCompatibleChatAdapter.java`：`RestClient` 调 OpenAI 兼容 `/chat/completions`，`Authorization: Bearer ${RAG_CHAT_API_KEY}`；不可用时抛 `BusinessException("rag_chat_unavailable", ...)`
- 单测：请求体结构、超时、空 key 报错、响应对齐（`choices[0].message.content`）

### 提交 2：`RetrievalFacadePort` 的 knowledge 封装 + `ContextAssembler`

- `infrastructure/adapter/KnowledgeRetrievalFacadeAdapter.java`：注入 `KnowledgeRetrievalService` + `KnowledgeService`，实现 `search(...)` 与 `chunksOf(...)`（按 `documentId` 批量取 `listChunks`，归一化 chunkId）
- `application/ContextAssembler.java`：
  1. 用 `chunksOf` 把 top-K 命中补全为**全文**（绕开 300 字预览）
  2. **扩展**：按 `sequence_no ±1` 与同 `headingPath`（每命中 ≤ `sectionCap`）补充上下文，受 `budget` 截断（**默认参数：邻居±1 + 同章节≤4、每次查询新增 ≤1500 字符**，来自已实测的实验）
  3. **排序**：按 *Lost in the Middle* 把最强证据放首尾（top1 开头、top2 结尾，中间按分数降序）
  4. 每段带 `[n]` 编号 + `documentTitle` + `headingPath`
- 单测：扩展命中、预算截断、首/尾排序、编号连续、同 `headingPath` 合并去重

### 提交 3：`RagAnswerService` + `AnswerCitationValidator`

- `application/RagAnswerService.java`：
  - `answer(RagAnswerRequest)`：`facade.search` → `assembler.assemble` → 若**候选为空 → 直接 `NO_CONTEXT` 拒答**（不调 LLM，省钱防幻觉）→ 拼 prompt → `chatClient.chat` → 解析 → `validator.validate` → 产出 `RagAnswerOutcome`
  - **生成侧降级**：LLM 不可用（捕获 `rag_chat_unavailable`）→ 返回 `degraded=true` + 只给检索片段 + 提示语，**不是 500**（与 knowledge 的「重排/关键词可降级」语义一致）
- `application/AnswerCitationValidator.java`（拒答的第三层，来自 research-6 / GopherCite / AbstentionBench 的结论：提示词不解决拒答，必须服务端校验）：
  1. 引用 `chunkId` 必须属于**本次检索候选集合**；
  2. 引用 `quote` 必须能在对应切片的**原文**（或 `headingPath`）中子串匹配；
  3. 任一失败 → `RefusalReason.INVALID_CITATION`，按「知识库没有记录」兜底
- 单测：空候选直接拒答；三个校验分支；降级路径；prompt 包含 grounding 指令

### 提交 4：`RagAdminController` + 装配 + 真实联调

- `api/web/RagAdminController.java`：`POST /api/v1/admin/rag/answer`，请求/响应契约见第五节（先 admin，公开端点+限流留到下一步）
- `mindora-app/config/RagModuleConfiguration.java`：按 `KnowledgeModuleConfiguration` 范式装配 `chatClientPort`（`@ConditionalOnProperty(mindora.rag.chat.enabled, matchIfMissing=true)`）+ `unavailableChatClientPort`（`@ConditionalOnMissingBean`）；`retrievalFacadePort`、`contextAssembler`、`ragAnswerService`
- 联调：10 条负例全部拒答；5 条正例引用可定位；模拟断网验证降级
- `mindora-app/pom.xml` 增加 `mindora-rag` 依赖

## 五、接口契约（先定死，再编码）

```http
POST /api/v1/admin/rag/answer
Authorization: Bearer <SUPER_ADMIN>
Content-Type: application/json

{
  "query": "Redis 的常见缓存问题和解决方案？",
  "scope": "all",                // 今天只接 admin；公开版固定 public
  "topK": 8,
  "rerankEnabled": true,
  "keywordEnabled": true,
  "expansion": true,             // 检索后扩展开关（默认 true，已实测 +3.5pt）
  "conversationId": null         // 预留：多轮记忆（今天忽略）
}
```

```json
200 OK
{
  "answer": "……[1][2]",
  "citations": [
    {
      "index": 1,
      "chunkId": "…",
      "documentId": "…",
      "documentTitle": "…",
      "headingPath": "…",
      "sourcePath": "…",
      "articleSlug": "…",
      "sequence": 12,
      "quote": "从原文逐字复制的片段"
    }
  ],
  "retrieval": {
    "latencyMs": 412, "vectorCandidates": 30, "keywordCandidates": 30,
    "matchedTopK": 8, "expansionApplied": true, "contextChars": 2987
  },
  "refused": false, "refusalReason": null,
  "degraded": false, "degradedReason": null
}
```

**引用定位（可检索定位的兑现）**：`citations[i]` 的 `chunkId + sequence + headingPath + sourcePath + articleSlug` 让前端能跳回原文；`quote` 是服务端从切片原文**逐字复制**的片段（不是模型改写），用于页内高亮。

```yaml

      enabled: true
      provider: ${RAG_CHAT_PROVIDER:siliconflow}        # 或 bailian

      timeout-ms: ${RAG_CHAT_TIMEOUT_MS:15000}
    context:
      budget-chars: ${RAG_CONTEXT_BUDGET:4000}           # 总上下文预算
      expansion-enabled: ${RAG_CONTEXT_EXPANSION:true}   # 检索后扩展开关
      expansion-added-chars: ${RAG_EXPANSION_ADDED:1500} # 扩展新增上限（实测拐点）
```

## 七、召回率策略（用数据，不凭直觉）

| 手段 | 依据 | 默认 |
| --- | --- | --- |
| **检索后扩展**（邻居 ±1 + 同章节 ≤4、新增 ≤1500 字符） | 实测 SpanHit@8 **88.1% → 91.6%**，优于提高 k | **开启**（可关） |
| 保持 top-8 检索 | *Lost in the Middle*：20→50 篇仅 +1.5%，top-8 已够；*The Power of Noise*：高分但无关的片段反而有害 | 保持 |
| **不把 k 提到 20** | 实测扩展（91.6%）> 提 k（90.1%） | 不提 |
| **不做文档配额去重** | 实测 −6.9pt（本项目答案常是同文档多块） | 不做 |

## 十、风险与回退

- **`AdapterHttpFactories.withTimeout` 是 package-private**：rag 适配器自带一个 ~15 行的等效工厂，不改 knowledge 的包边界（备选：把该方法改为 `public`，影响更小但动了别人的模块——选前者）。
- **LLM 输出引用格式不稳定**：prompt 用强约束（JSON schema + 明确示例），但**最终兜底靠服务端 `AnswerCitationValidator`**，不依赖模型自觉。
- **真实联调依赖 LLM 密钥**：`RAG_CHAT_API_KEY` 从 `mindora-local.yml` / 环境变量读，不进仓库；联调失败先报「密钥未配置」而不是静默降级。
