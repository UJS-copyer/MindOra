# RAGNote 调研与架构优化启示录

> **文档定位**：记录同类优秀项目 `RAGNote`（面向个人知识管理的全栈博客与 RAG 智能问答系统）的核心设计思想、架构方案与技术细节，并结合我们当前项目（Mindora 全栈知识库 / 博客系统，已打通 `Obsidian → Gitee 仓库 → 知识库手动同步`）进行针对性借鉴与落地规划。
>
> **维护日期**：2026-10-17（新增第五节：RAGNote V2 新信息与阶段路线裁决；前四节保留为 V1 时期的调研映射）。

---

## 一、 对标项目（RAGNote）核心概览

- **定位**：全栈个人知识管理 + 博客 + RAG 智能问答系统（“可写、可存、可检索、可对话的个人第二大脑”）。
- **技术栈**：
  - 前端：Vue 3 + Vite + Ant Design Vue + md-editor-v3（视觉风格参考改造自 astro-theme-pure）。
  - 后端：Java 21 + Spring Boot 3.4.x + Spring AI + MyBatis-Plus + Redis + Spring Security。
  - 检索/RAG：Milvus（向量） + Lucene（关键词倒排）混合检索（Hybrid Search），通过 RRF（倒数排名融合）+ Reranker 重排序。
  - 存储/资产：MySQL + 本地/Cloudflare R2 对象存储。
  - 部署与运维：Docker + Nginx，支持按服务器资源情况**按需启停向量模块**。

## 二、 核心启发与设计反思

### 1. 知识切片（Chunking）：从“长度切分”到“富元数据语法树切块”
* **痛点反思**：常规按 500~1000 字符固定窗口或纯换行切片，容易割裂代码块、表格，且丢失上下文关系。
* **RAGNote 方案**：
  - 基于 Markdown AST 解析文档，提取段落、代码块、表格、FAQ 等结构。
  - 每个切片附加丰富的结构化元数据：
    - `titlePath`：完整的标题层级路径（如：`后端技术 > Spring Boot > AQS 原理解析`）。
    - `headingLevel`：标题级别（H1~H4），标识内容所处的信息层级。
    - `blockType`：块类型（如 `paragraph`, `code`, `table`, `callout`）。
    - `codeLanguage`：代码块语言（如 `java`, `typescript`）。
* **对我们项目的启发**：
  - 我们的内容源来自 Obsidian，天然具备严密的目录大纲和 H1~H4 树状层级。
  - 在 `mindora-knowledge` 的解析管道中，应构建 AST 解析器，在切片时注入 `titlePath`、`blockType` 等元数据。
  - 在大模型组装 Prompt 时，检索到的上下文附带标题路径，能显著减少幻觉，并实现代码块/表格的原生精准引用。

---

### 2. 问答场景分层：双层问答闭环（全库 vs 篇章伴读）
* **痛点反思**：很多知识库只提供全站维度的独立问答页面（`/chat`），读者在阅读长篇文章遇到疑惑时，无法即时追问。
* **RAGNote 方案**：
  - **全库全局问答**：跨所有文章与资料的综合对比、探索与知识关联。
  - **文章详情页侧边栏问答**：针对当前文章的内容进行局部总结、提问、概念释义。
* **对我们项目的启发**：
  - 在 `frontend/apps/site` 的文章详情页新增“侧边栏/抽屉式 AI 伴读助手”。
  - **工程效益**：篇章级追问只需锁定当前文章的切片，无需进行全库跨度召回，**响应更快、召回精度接近 100%、Token 开销大幅降低**，并支持“一键生成文章提纲/要点”、“针对本文提问”。

---

### 3. 内容流转与生命周期：解耦“知识库沉淀”与“公开发布”
* **痛点反思**：Obsidian 中的笔记往往包含草稿、报错随笔、私密记录和深度技术长文。如果所有笔记都直接同步到公开发布列表，会导致站点内容杂乱。
* **RAGNote 方案**：
  - 将 Obsidian 导入的内容默认作为“草稿（Draft）”沉淀。
  - 明确拆分“文章发布（是否前台可见）”与“知识库同步（是否切片入索引库）”。
* **对我们项目的启发**：
  - 结合当前的 `Obsidian → Gitee → 知识库同步`，建立**三态内容生命周期**：
    1. **私有知识沉淀态**：Obsidian 同步入库的所有笔记均切片入私人知识库，作为个人私有 AI 助手的数据源。
    2. **公开博客发布态**：通过 Frontmatter 标签（如 `published: true`）或后台开关，筛选出成熟文章展示在前台。
    3. **索引状态维护**：支持单独对某些文章执行“从向量库移出”、“重新切片入库”、“刷新缓存”等细粒度运维操作。

---

### 4. 检索链路演进：混合检索（Hybrid Search）与可视化可观测性
* **痛点反思**：纯向量检索容易出现“语义相近但专有名词完全不对”的问题，尤其在代码报错、API 方法名、特定配置项等精确匹配场景表现较差。
* **RAGNote 方案**：
  - 向量检索（Milvus）负责语义宽泛匹配，倒排检索（Lucene）负责专有名词精确匹配。
  - 通过 **RRF（Reciprocal Rank Fusion）** 融合多路召回列表，再经过 **Reranker（重排序模型）** 精细打分。
  - **后台调试面板**：内置“Rerank 效果测试”、“上下文压缩测试”与“问答审计日志”。
* **对我们项目的启发**：
  - 在 `mindora-rag` 演进路径中，规划 Lucene / 数据库全文检索 + 向量检索的混合检索架构。
  - 在 `mindora-admin` 后台搭建**检索可视化调试器**：输入一个 Query，直观展示向量召回 Top N、关键词召回 Top N、融合打分结果及重排模型打分变化，极大降低算法调优难度。

---

### 5. 架构韧性与成本控制：模块按需启停与优雅降级
* **痛点反思**：个人或轻量级服务器内存与算力有限（Milvus、Embedding 模型、Reranker 占资源较高），一旦服务超载可能拖垮整个站点。
* **RAGNote 方案**：
  - **架构解耦**：向量检索模块支持在配置文件中一键关闭；关闭后自动降级为关键词检索或纯静态展示。
  - **风控与限流**：后台可动态控制问答权限（公开、仅登录、仅管理员），并结合 Redis 实施接口限流。
* **对我们项目的启发**：
  - 充分利用 Mindora 当前的多模块（`mindora-knowledge`、`mindora-rag`、`mindora-blog` 等）优势。
  - 后端增加“降级运行”机制：当 Milvus 服务不可用或被禁用时，自动退化为基础搜索，不阻塞常规博客浏览与管理功能。
  - 问答模块提供基于 Token 或调用次数的平滑限流与权限分级控制。

## 四、 落地进展（Stage 3 第一轮）

本轮（Stage 3 第一轮「检索底座」，F0a–F10）围绕 Markdown 富元数据切片、向量检索与管理端调试进行了完整实现与实测验证：

1. **切片元数据化与向量 Payload 富化**：
   - 重写 Markdown 切片为带标题路径的块级解析器（F1/F2），V6 迁移在 `knowledge_chunk` 表中固化 `heading_path`（`A > B > C` 层级路径）、`heading_level`（H1~H6）、`block_type`（paragraph、code、table、callout、heading 等）、`code_language` 与 `content_hash`。
   - 向量 Payload 全面富化（F4），写入 `chunkId`、`documentId`、`versionId`、`sequence`、`sourceType`、`sourceId`、`sourcePath`、`visibility`、`status`、`knowledgeEnabled`、`blockType`、`contentHash`、`articleId` 等业务与权限字段；向量点 ID 统一对齐 `chunkId`，消除了此前 `documentId:index` 导致的错配。

2. **存储架构取舍：正文不入向量库、按 Chunk ID 回查 MySQL**：
   - Qdrant 向量库仅持久化稠密向量（`dense` 1024 维）与轻量过滤元数据，不冗余存储切片大文本（`content`），大幅降低向量存储内存与带宽开销。
   - 检索时由 Qdrant 召回命中的 `chunkId`（Point ID），再通过 `mindora-knowledge` 批量从 MySQL 回查正文及完整文档信息（如 `documentTitle`、`sourcePath`、`articleSlug` 等），兼顾检索效率、数据一致性与存储经济性。

3. **检索读取链路与 Fail-Closed 权限过滤**：
   - 新增向量检索读取能力与 Qdrant 搜索适配（F5），构建检索编排服务（F6），支持两阶段召回与重排序流程。
   - 检索执行前严格应用 Fail-Closed 权限过滤，根据调用上下文与知识库/文章可见性规则（`status`、`knowledgeEnabled`、`visibility`）构筑 Qdrant filter，确保未公开或无权限切片在检索源头被彻底隔离，杜绝越权召回。

4. **实测 Rerank 余额不足触发 Fallback 优雅降级**：
   - 为 Embedding 与 Rerank 适配器增加超时控制与可配置降级策略（F3）。
   - 在 Stage 3 第一轮端到端联调实测中，SiliconFlow 账户余额不足导致 Rerank API 返回 HTTP 402，服务依据 `fallback-enabled=true` 配置自动降级，按向量相似度原始得分保底返回，并在响应中标记 `fallback=true` 与 `fallbackReason`，实测验证了降级链路的高可用韧性。

5. **端到端联调发现并修复的缺陷**：
   - **Qdrant 命名向量检索格式错配**：Qdrant `POST /collections/{collection}/points/search` 接口检索命名向量时，JSON 请求体必须使用 `{"name": "dense", "vector": [...]}` 格式；此前沿用写入时的 `{"dense": [...]}` 键值映射会被 Qdrant 报 400 Bad Request 拒绝。现已修正并补充专项回归测试。
   - **段落紧邻围栏代码块丢失识别**：原解析器在普通段落与 ` ``` ` 围栏代码块之间缺少空行时，会将代码块内容误吞并入段落，导致 code 块和 `blockType` 丢失。现已调整状态机判定，紧邻围栏直接触发段落收口，并补充测试用例。

**对本项目的意义**：V2 的三处变化都不是「加功能」，而是**减法**——在线不用向量、能力交给工具、质量交给闭环记录。与本项目「简单舒适优先」同向；但**减法也要用自己的数据验证**（见 5.3）。

### 5.2 与「真实 RAG 项目」的差别（口径固定）

「真实 RAG 项目」此处指有生产流量的通用 RAG 产品（含 RAGNote V2）。四处结构性差别：

| 维度 | 业界常见 | 本项目（rev2：分型拒答 + 服务端摘录） | 收益 / 代价 |
| --- | --- | --- | --- |
| 答不上来时 | 一句拒答，或阈值/低置信兜底 | **三态（rev2）**：`grounded` 有依据作答；`ungrounded` 无依据兜底（信息说明 + 可选常识 + 建议追问，**不带引用**）；`refused` 仅安全类。零候选时**多调一次小模型**判域并写说明。**不做分数阈值**（正例最低 0.0008、负例最高 0.8324，区间完全重叠） | 收益：不把访客堵死，也不拿模型常识冒充站内资料；代价：零候选多一次小调用，判域全押在模型上 |
| 引用 | 事后归因（把答案句子映射回片段）或 LLM 评判 | **服务端摘录 + 编号校验（rev2 取消逐字门禁）**：`quote` 一律由服务端从切片截取；编号越界只丢该条引用，**不拒答** | 收益：作答率与表达自然度上升、零额外模型调用；代价：不再能声称「模型每个字都在原文里」，只剩「引文来自原文且可回链」（design-11 §15.1） |
| 管线 | 改写 → 检索 → 重排 → 生成 → 校验/精修 | **单次生成 + 确定性校验**（一个 LLM 调用，其余是代码） | 收益：首字延迟与费用低；代价：缺 query 改写补偿（3.7 条件化补） |
| 质量评估位置 | 离线评测集（RAGAS 类）为主 | 在线应答三态（含无依据兜底）+（4.3 起）在线评价；离线只有 323 条黄金集 | **两者不重叠、不能互相替代**：不能用「引用可回链」冒充「答得对」，也不能用离线分数冒充线上体验 |

**对 query / answer 的裁决（配套）**：

1. **query：只在 3.7 做条件化改写**（有历史才触发、失败兜底原 query、三问对照验证），不做 HyDE / Multi-Query。约束不变：改写结果**只用于检索**，不得替换写入 prompt 的用户原句。
2. **answer：仍不做生成后的 LLM 二次改写 / 润色，但理由已变（rev2）**。不再是「引用不变式」——逐字门禁已取消，那个理由随之失效。现在的理由是**没有收益**：模型本就该基于给定片段自行组织措辞，再调一次模型只增加延迟与失效点（流式首字延迟翻倍），并不提升质量。要更自然就改提示词或换模型（design-11 §7.2）。
3. 「答案相关性校验（NLI / verifier）」继续暂缓。rev2 取消逐字门禁后，这条的**优先级反而下降**：我们不再声称答案忠实于原文，也就不必为「支撑度」背书；它只在 4.3 的评价数据显示「引文来自原文但结论答偏」占比 > 10% 时再引入（届时以评价数据为准，不预设）。

### 5.3 裁决一：向量检索保留，只改降级语义（A/B 降为 backlog）

**裁决（rev2）**：**向量保留，不排期下线**。A/B 降级为 backlog（要做时按下面的参数执行）。但**现在就要改一条语义**：向量库不可用从「能力缺失 → 硬报错」改为「质量降级 → 纯关键词」——语义已改到 `docs/design-10-keyword-retrieval-and-hybrid-fusion.md` §5。

依据（按强度排序）：

1. **我们从未测过单路**：323 条黄金集只测过「双路 hybrid + 检索后扩展」；`vector-only` / `keyword-only` 的 `DocHit/SpanHit` **一个数字都没有**（`scripts/rag-eval/README.md` §3 里那行「只用向量单路（做 A/B）」的命令其实是上一条的复制粘贴）。「向量有用」目前是**未验证的默认值**；但没数字也不能反过来当成「砍掉它」的依据——**未验证 ≠ 无用**。rev2 据此改判：先保留、先修降级语义。
2. **RAGNote V2 的弃用是外部旁证，权重有限**：他们是「保留能力、在线不用」（V2 原文 L275–277），理由偏运维。而这条理由在本项目**更硬**：Qdrant 是唯一必须跑在 VM 容器里的检索组件，VM Docker 网桥丢 IPv4 已复现 **4 次**（`stage-3.5-task-manifest-cn.md` §4）；design-10 §5 又规定「向量库不可用 = 能力缺失 = 明确报错」——**公开问答当前硬依赖一个已经坏过 4 次的基础设施**。关键词单路（Lucene 进程内）可把在线外部依赖从 2 个（embedding + 向量库）降到 0。
3. **他们的结论不能直接搬到我们的语料**：他们是中文技术长文 + 全文检索；我们的语料是 Obsidian 笔记，`vague`（口语化）34/202、`fact` 38/202，正是语义召回的主场。**必须自己测。**

A/B 设计（**backlog：参数先定着，将来要做或质量/成本报警时照此执行**）：

- **臂**：2×2 = {向量 on/off} × {重排 on/off}；**同一次索引重建后连跑**；黄金集 323 条。负例只有 10 条 → **只判命中，不判拒答率**。
- **主指标** `SpanHit@8`；辅 `DocHit@8`、`MRR`、分类型（`vague` / `fact` / `code` / `overview`）、耗时与外部调用次数。
- **判定门槛**：Δ = hybrid − keyword_only，**以 2pt 为「实质差异」**。这是本项目经验口径而非行业标准，旁证是「把 k 从 8 提到 20」这类强干预也只值 +2.0pt（`rag-retrieval-improvement-survey-cn.md` §3.1）。
  - |Δ| < 2pt → 向量无实质贡献 → 公开链路走关键词单路；
  - Δ ≥ 2pt 且集中在 `vague` / `fact` → 向量不可替代，保留 hybrid；
  - Δ ≥ 2pt 但只集中在 `code` / `cross-section` → 关键词主场已覆盖，向量可下线。
- **失效断言（必须有，否则整轮作废）**：每次请求校验 `fallback=false`、`keywordFallback=false`、检索模式与预期一致。史实：SiliconFlow 曾因余额不足返回 402 触发自动降级（本文 §四.4）——降级轮测出来的是降级链路，不是重排能力。
- **如果哪天真的下线**（形态先设计好，避免临时拍脑袋）：
  - 配置 `mindora.rag.retrieval.mode=hybrid|keyword`（进 design-10 §7 配置表），公开端点取该值；
  - 向量索引**继续维护**（入库照旧，管理端检索调试页可切回 hybrid 对照）；
  - 响应与 SSE `done` 增加 `retrievalMode`——否则线上答案与管理端复测不在同一配置下，复测结论不可迁移（这正是 RAGNote V2 自己强调的坑，L563）。

### 5.4 裁决二：Stage 4 重排后的优先序

| 序 | 项目 | 为什么在这个位置 | 边界（防止做成 RAGNote 全套） |
| --- | --- | --- | --- |
| 4.1 | **公开域收紧为「已发布」** | 先定义「能问什么」：域不收敛，后面的应答三态与记录都没有基准；顺带补掉 unpublish 缺口 | 只收紧**公开域**；草稿照旧入库供管理端问答（design-11 §15.3） |
| 4.2 | **回答契约 v2 + 提示词版本化**：三态（有依据 / 无依据兜底 / 拒绝）+ 服务端摘录引用 + 取消逐字门禁；prompt 移到后台（可改 / 有历史 / 一键回退） | 「答不上来」要变成可解释的说明；而契约的载体就是 prompt——**先外置再改契约**，否则「改一句要发版」立刻反噬 | 判域与作答/兜底同一次调用；**零候选才允许判「域外」**；占位符缺失拒绝发布（design-11 §15、§16） |
| 4.3 | **问答记录 + 评价（质量闭环最小版）** | 契约稳定后才装表，字段不返工；后面每个「值不值得」都要靠它出可比数据 | 只记 `rag_chat_log`（query / `answerMode` / `ungroundedReason` / 引用数 / 越界数 / degraded / latency / **配置快照**）+ 一条评价（有帮助 / 没帮助 + 原因枚举）；**不落**完整 prompt 与上下文（design-04 明令）、不做 BI |
| 4.4 | **韧性与成本护栏** | 公开站不能因为一个可选依赖挂掉就整条问答硬失败（design-10 §5 已改语义） | 向量挂→关键词、重排挂→融合序、模型挂→摘录、关键词挂→向量；单问预算与日上限；降级必须显式标记 |
| 4.5 | **运维可视化** | 原 Stage 4 的 Operations 部分 | 4 类失败可见 + 可重试 + 降级告警；不做告警平台、不做计费报表 |
| 4.6 | **双问答入口（仅预填）** | 零契约成本的动线改进 | 真伴读（锁定本文检索）推迟到公开篇数 ≥ 20；检索契约当前无 `documentId` 过滤（design-10 §6.1） |

顺序之外的三条硬前置：**3.6 管理端问答 + 会话页**（4.3 的记录页与 `chat_conversation` 的数据来源都靠它）、**3.7 查询改写**、**T1 语料凭据处置**（公开暴露前门禁，本人操作，未闭环）。
**Backlog（不排期）**：向量 / 重排 A/B（参数见 5.3）、真实伴读、语义缓存。

### 5.5 裁决三：「最终形态」与永不做的清单

以「2 篇公开文档、即将扩充到几十/几百篇」为前提：**done 不是功能对齐 RAGNote，而是「每条能力都有实测依据 + 一次真实使用不别扭」**。八条可判定标准（D8 即「生产级」定义里"体验接近常见产品"的落地形态，定义见 `docs/design-01-product-scope.md` §范围复核）：

| # | 判据 | 验法 |
| --- | --- | --- |
| D1 | 公开文章 ≥ 20 篇，`articleSlug` 非空率 100%；**由作者从草稿中挑选手动发布**（不做自动/批量发布） | 后台统计 + 抽样点引用回链 |
| D2 | 通用式黄金集 `DocHit@8` ≥ 95%、`SpanHit@8` ≥ 90% | 全量重建索引后复跑，与基线差 ≤ 1pt |
| D3 | 端到端正例 ≥ 15/15；**兜底与拒答必须分型正确**（域外问题走 `ungrounded/no_domain_match`、主题相关但缺资料走 `ungrounded/no_retrieval_result`、安全类走 `refused`）；出「答不上来」的回答**零引用**；`grounded` 回答**零越界引用**（`chunkId` 在候选内、quote 为服务端摘录、可回链） | 联调脚本 + 线上记录抽检 |
| D4 | 100% 问答有记录与配置快照；评价可写；管理端「会话 → 记录 → 同问题复测」实测走通一次 | 人工走查 |
| D5 | 拒答时能说出「本站有什么、可以怎么问」，且公开篇数 < 20 时不误导 | 2 篇语料下逐条看拒答文案 |
| D6 | 一键启动文档可复现；同步 / 索引 / 检索 / 生成 4 类失败可见可重试；单实例约束有明确报错 | 按 `development-startup-cn.md` 冷启动一次 |
| D7 | `rag-guide-cn.md` 各章指向的代码仍存在，无「文档写了代码没做」 | 逐章核对 |
| D8 | **体验基线（「接近常见产品」的具体化）**：① 流式有首字反馈且可中断；② 错误分型可读（限流 / 降级 / 失败）且可重试；③ 答案可复制、可重新生成；④ 每条答案可评价（赞 / 踩）；⑤ 360px 宽度可用 | 逐项人工走查（配合 4.3 记录） |

**D1 的性质要注意**：内容篇数是**产品可用性**前提，不是**工程 done** 前提。作者没写够 20 篇，工程仍可判 done（D2–D7 全绿）；但那时「公开问答是否值得给访客用」应给出否定答案，而不是继续加功能。

**永不做的清单**（写进路线，避免后续会话重新论证）：

1. Agentic RAG / 多工具编排 / MCP 接入
2. GraphRAG / RAPTOR / 多粒度摘要索引
3. 父子块与多向量检索（已被「检索后扩展」覆盖：88.1% → 91.6%，design-11 §6）
4. 生成后的 LLM 二次改写 / 润色（无收益且延迟翻倍，见 5.2）
5. HyDE / Multi-Query（除非 3.7 三问对照显示 > 2pt）
6. 相似度阈值熔断（正负例分数区间重叠）
7. 公开注册 / 评论 / 点赞 / 排行榜 / 通知 / 邮件
8. 多租户 / 组织 / 权限编排
9. 多模态入库（图片 / OCR / 视频）
10. 自训 embedding / rerank 微调 / 自研向量库
11. 在线 A/B 平台与「评价自动反馈进索引」的自动学习回路
12. 多实例 / 分布式索引 / 高可用（单实例是设计前提，不是欠债）
13. 后台 BI 大屏 / 精细额度计费
14. 移动 App / 桌面端

### 5.7 生产级 RAG 的最小集（rev2 新增：项目要上线）

「生产级」的**定义**（2026-10-17 定稿，落 `docs/design-01-product-scope.md` 范围复核）：
**能给陌生人用、不烧钱、坏了能发现、改了能回退、问答体验接近常见产品**；明确不含多实例 / 高可用 / SLA。

按这五条拆成下面 9 项能力，必须齐全，其余都可 backlog：

| # | 必备项 | 落点 |
| --- | --- | --- |
| 1 | 知识域确定（公开 = 已发布，fail-closed，补 unpublish 缺口） | 4.1 |
| 2 | 引用可追溯（`chunkId` + 服务端摘录 + 回链原文） | 4.2 |
| 3 | 拒答可解释（域外 / 未收录 / 资料不足，且说得清本站有什么） | 4.2 |
| 4 | 质量闭环（记录 + 评价 + 配置快照 + 同题复测） | 4.3 |
| 5 | 降级矩阵完整（4 类失败各有退化路径，且**显式标记**） | 4.4 |
| 6 | 成本护栏（单问预算、日/月上限、超限行为） | 4.4 |
| 7 | 滥用护栏（限流 + 可信代理解析 `X-Forwarded-For` + 并发上限） | 4.4 / Stage 5.1 |
| 8 | 观测与告警（4 类失败可见、降级告警、uptime 探针） | 4.5 / Stage 5.3 |
| 9 | 凭据与合规（T1 闭环、SecretGuard、隐私声明与 AI 免责） | Stage 5.4 |

**「改了能回退」的落地**：不只是回滚部署——提示词进后台、有版本历史、可一键回退（design-11 §16，随 4.2 交付）；配置项同理走 yml 覆盖。
「体验接近常见产品」的落地：见 D8（首字反馈可中断、错误可读可重试、可复制可重生成、可评价、窄屏可用）。

**最大结构风险（现在就要认，或现在就要改）**：进程内 Lucene 是单写者 → 后端**不能水平扩展、重启即停机**。上线等于接受「单实例 + 维护窗口」。将来若必须扩容，选项是换外置检索（OpenSearch/ES）或读写分离——成本远高于现在，所以**现在不改，但必须写进运维事实**，不能假装它不存在。

**与「个人项目」定位的张力**：产品面保持小而个人（不做社交、多租户、平台化），工程面按可上线标准。调和判据是：任何新功能先问一句「它是否新增一条运维职责」，是就进 Stage 5 清单，不是才做。

### 5.8 「多用户」与「多租户」是两件事（成本评估）

先把概念分开——参考项目 RAGNote 是**多用户**（一个站点、多个读者账号、共享同一知识库），**不是多租户 SaaS**。

| | 多用户（参考项目那种） | 多租户（一套部署多个独立站点/知识库） |
| --- | --- | --- |
| 已有基础 | `user_account` / 角色 / 会话 `user_id` / 限流按 `userId` 分桶 / JWT —— **大部分已具备** | 无 |
| 主要缺口 | 公开注册（含验证）、个人空间页、会话前端的归属入口 | 核心表加 `tenant_id` + 唯一约束改复合 + 全量查询带租户条件；检索两侧过滤加租户；JWT 加 tenant claim；资产路径隔离；越权测试矩阵 |
| 估算工作量（**估算，非实测**） | **4–6 人日（≈1 周）**，不触及检索与索引 | **12–20 人日（≈3–4 周）纯改造**，期间不能做 feature |
| 风险等级 | 常规功能风险 | **安全级**：漏一处 = 跨租户数据泄漏，不能靠抽查验收 |
| 结构冲突 | 无 | **与单实例 Lucene 冲突**：写锁是进程级单写者，多租户共享实例时索引重建会互相阻塞 |

**结论：多用户随时可做（1 周级），多租户明确不做。** 参考项目的「多用户」能力（注册、等级、徽章、评论审核）我们只取账号与会话归属，其余仍在「永不做的清单」里。

**现在就能留的三个零成本兼容点**（避免将来返工，不花额外时间）：

1. 权限判定统一走一个 `AccessContext`（调用者身份 + scope），不要散落在 controller 里逐个判断；
2. 检索过滤条件由**同一个方法**生成（design-10 §4.2 已经如此，且有测试断言两路相等）——将来加租户只改这一处；
3. 任何地方都用 `currentUserId()`，不要出现「单用户」硬编码假设（表里已有 `user_id`）。

**触发条件**（什么时候才值得动）：出现第二个作者，或第二个独立知识库。在此之前的投入都是负收益。
