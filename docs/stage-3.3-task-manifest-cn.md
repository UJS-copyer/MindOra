## F1：切片推进量塌缩修复

### 现象

真实语料统计（2195 个有效切片）：

- 长度 < 50 字符的切片 **634 个（28.9%）**；< 150 字符占 **60.3%**；
- 13 篇文档完全没有 `heading_path`，其中「初稿优化」154 个切片、「个人知识库开发记录」83 个。

拉取「个人知识库开发记录」的切片序列后发现：**1857 字符的源文档产出了 83 个切片，且切片之间是逐字符位移的近重复**：

```
seq 1 : 120 字符  "打开一个默认浏览器页面…"
seq 2 : 119 字符  "开一个默认浏览器页面…"   ← 仅少了第一个字
seq 3 : 118 字符  "一个默认浏览器页面…"
```

源文档内容完全正常（每行一条问题记录，换行清晰），因此**不是数据脏，是切分器缺陷**。

### 根因

`MarkdownChunker#splitText` 从 `start + chunkSize` 往回找最近的换行作为切点。当**一条短行后面紧跟一条超过 `chunkSize` 的长行**时，回溯到的换行点紧贴 `start`，于是 `end - overlap` 落在起点之前，前进量被 `Math.max(start + 1, …)` 兜成 **1 个字符**，循环退化为逐字符推进，直到爬完那条短行。退化切片数量 ≈ 该短行的长度。

### 修复

- **只接受足够长的窗口**：换行切点必须满足 `boundary - start >= minWindow`，其中
  `minWindow = max(minimumSize, overlap + (chunkSize - overlap) / 2)`；
  否则按窗口边界硬切，并在窗口末尾 1/5 范围内回退寻找**安全切点**（标点/空白之后），尽量避免把单词从中间切断。
- **保证单次推进量不小于 `minAdvance = minWindow - overlap`**，循环必然终止，邻居切片不再近乎重复。
- 保留原有语义：`overlap` 仍然生效（`end - overlap >= start + minAdvance` 恒成立，`max` 分支实际不会触发）。

### 验证

**单元测试**（`MarkdownChunkerTest`，20 → 23 个用例，全部通过）：

- `doesNotEmitNearDuplicateChunksWhenShortLinePrecedesLongLine`：短行 + 长行 → 切片数 ≤ 3、无互相包含、无重复；
- `keepsChunkCountBoundedForUnbrokenLongText`：无换行长段落 → 切片数受推进量约束；
- `stillSplitsNormalNotesIntoFewChunksWithHeadingContext`：正常笔记行为不变。

**算法仿真**（修复前后对比，`logs/chunker-sim.mjs`）：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 正常笔记（每行 45 字符） | 2 个切片 | 2 个切片（不变） |
| **短行 + 超长行** | **82 个切片**（120,119,118… 总字符膨胀 6.22x） | **2 个切片**（膨胀 1.10x） |
| 无换行长段落 | 3 个切片 | 3 个切片 |
| 中英混排 | 3 个切片 | 3 个切片 |

**真实数据复验**（后端加载修复后单篇重建索引）：

| 文档 | 修复前切片 | 修复后切片 | 平均长度 |
| --- | --- | --- | --- |
| 个人知识库开发记录 | 83 | **2** | 724 |
| 初稿优化 | 154 | **73** | 169 |
| Redis-黑马点评项目笔记 | 28 | 28（不受影响） | 209 |

修复后「个人知识库开发记录」的两个切片是正常的长文本块（761 / 686 字符），不再有逐字符位移的重复。

1. **缺陷的实际影响面比最初估计小，且集中在 50–149 字符区间**。该区间减少 139 个切片，与两篇复验文档的减少量（83 → 2、154 → 73）吻合；说明塌缩产生的主要是 50–149 字符的切片，而不是 < 50 字符那一批。
2. **`<50` 字符区间几乎没变（634 → 614）**，因此「语料中 28.9% 的切片不足 50 字符」**并非**本次修复的缺陷所导致；把两者直接关联是过度归因，此处更正。
3. **先前用于圈定影响范围的 inflation 指标（切片数 ÷ 源长度/800）在重建前后完全一致**（如 codex SSH 15、数据结构 15、论文绘图提示词 107）。这说明该指标主要反映「文档结构本来就碎 / 代码块与表格是原子块」，**不能作为该缺陷的代理指标**；判断缺陷应以「相邻切片是否逐字符位移的近重复」为准。
4. 修复是必要且有效的（消除了索引中的近重复污染、无标题切片减少 162 个），但**它不是当前语料小切片问题的主要成因**。

## F1 遗留发现：块类型交替导致碎片化（待决策）

修复推进缺陷后，「初稿优化」（源 21124 字符）仍有 **73 个切片、平均仅 169 字符、37 个不足 50 字符**。检查其切片序列后发现它们是**彼此不同的正常块**（不再重复），碎片化的原因是另一条规则：

`buildChunks` 在**块类型变化时立即 flush**。而该文档是「问题（列表）→ 回答（段落）→ 问题（列表）」交替书写，于是每两行就产出一个切片。

**这是一个设计取舍，不是 bug**：按类型 flush 能让切片的 `blockType` 元数据准确；代价是交替书写的笔记被切得很碎，而碎片缺乏上下文，对召回与重排都不利。F2 复测显示：它（连同「本来就一行一条」的短记录）是语料中剩余 **614 个不足 50 字符切片**的主要成因，已不再是推进塌缩缺陷。

可选方案：

1. **仅在缓冲区累积到一定长度时才按类型 flush**（例如达到 `minimumSize` 或 `chunkSize / 2`），混合块的 `blockType` 取首个块的类型或退化为 `paragraph`；
2. 保留现状，改为在切片后做**小块合并**（与现有 `mergeTrailingSmall` 类似，但面向任意相邻小块）。

方案 1 能同时减少切片数与提升单块上下文，但会牺牲 `blockType` 的纯度；方案 2 改动更小、语义更保守。**待评估后再决定**，建议先用 F3 的评测集量化「碎片 vs 大块」对 Hit@8 的影响，避免凭直觉改动。

### 关键设计

- **问题优先、锚点分级**：只标 L1 文档 + L2 关键片段，**不要求标切片 id**（随手笔记的切片边界本就模糊）；
- **SpanHit 用切片全文匹配**：脚本按返回的 `chunkId` 调 `GET /documents/{id}/chunks` 拉全文，回避 `contentPreview` 的 300 字截断；
- **同时看 DocHit 与 SpanHit**：两者差距本身就是切片质量的度量（DocHit 会因碎片而虚高）；
- **阈值分离分析**：输出正例命中切片的最低重排分与负例最高重排分，直接给出熔断拒答阈值。

### 候选题集的生成方式（首版 212 条）

1. 用 `logs/dump-corpus.mjs` 把 141 篇文档（2028 切片、508,919 字符）导出为纯文本，按字符数均衡分成 8 组；
2. 用 **8+6 个并行子代理**分片阅读并产出候选题，要求覆盖「精确符号 / 口语模糊 / 跨章节 / 整体理解 / 长块 / 跨文档」六类；
3. 用 `logs/validate-candidates.mjs` 过**逐字门禁**：文档标题必须真实存在、`keySpans` 必须逐字出现在目标文档的切片正文或 `headingPath` 中、问题不得重复；
4. 负例由 controller 自己构造并逐条 grep 核验「全语料确实没有」。

**门禁价值（实测）**：217 条候选中 **5 条被剔除**，全部来自同一个子代理**凭空编造**的片段（`sys.platform`、`client.retrieve(`、`punkt_tab`、`2026-06-17`、`# ==== Main ====` 在全语料中均不存在）。若不做逐字校验，这些无法回答的题会静默拉低基线。

### 两个必须纠正的结论

1. **`DocHit` 与 `SpanHit` 的落差（94.1% vs 72.3%）说明瓶颈不在「找不找得到文档」，而在「能不能定位到答案所在的那一块」**。`code`（97.9% vs 66.7%）与 `long-block`（100% vs 20%）是最典型的两类。
2. **「低分熔断拒答」这个方案在当前数据上不成立**。先前基于 7 条示例得出的「阈值 ≈0.28」是过拟合：正式基线显示
   - 正例中命中切片的最低重排分为 **0.0009**（有相当一批正例的重排分极低但确实命中了），
   - 负例中最高重排分为 **0.8324**（GraphQL 的 N+1 与语料里的 N+1 数据库内容语义相近，被重排模型判为高度相关）。
   两者**严重重叠**，单靠重排分无法分离。因此**拒答必须由生成层承担**（严格 grounding + 明确「知识库没有记录」），重排分只能作为成本优化的弱信号，不能作为正确性门禁。

- 按类型：cross-section 97.7%、long-block 100%、vague 91.4%、code 90.0%、fact 88.9%、**overview 79.6%**、**multi-doc 78.6%**

**必须说明的两点（诚实边界）**：

1. **「指代式提问会虚高命中」这一预判并未成立**——实测反而是指代式更低（78.6% vs 91.2%）。原因很可能是**混淆变量**：指代式题多是"精确符号题"（某个文件名、某个阈值、某个表格行），本身就落在难召回的小切片上；而通用式题多指向文档的主题内容（较大、较中心的切片）。**两个子集在难度与文档覆盖上并不等价，因此这个差值不能解释为"提问视角的因果效应"**。
2. 本次通用式批次由子代理按 `index.json` 下标区间取材，实测**存在区间重叠**（部分代理未严格守范围，实际重复覆盖了内容较丰富的文档、跳过了内容极薄的文档），因此覆盖面**不均匀**。这不影响"题面已符合公开场景"这一结论，但会影响绝对数值的可比性。

因此本轮的**核心产出是"口径修正"**（285/313 条为通用式，题面不再泄漏答案位置），而不是"某视角更准"的结论。

### 「上一轮修复是否必要」的客观证据

利用 `knowledge_chunk` 中**软删除（`failure_reason='archived'`）的上一代切片**做同口径对照，检测「相邻切片互为 1–5 字符后缀位移」这一缺陷签名：

| 范围 | 位移近重复对 |
| --- | --- |
| 修复前（全部归档代次） | **735** |
| 修复前（当前版本的上一代） | **147**（个人知识库开发记录 78、初稿优化 69） |
| 修复后（现役切片） | **0** |

**结论**：该修复消除了一个**可客观测量**的索引污染缺陷（近重复切片归零）；但它的**检索指标收益尚未被证明**，语料聚合影响也有限（切片 −7.6%）。因此 F1 的必要性依据是「正确性与可复现性 + 消除未来再次触发的风险」，而**不是**当前语料的指标提升——后者正是 F3 正式基线要验证的事。

## F4 前置：成熟方案调研与选型

按 `AGENTS.md`「先调研，后设计」，为「文档找得到、答案切片进不了 top-k」这一症状做了一轮**有来源**的调研，结论见 `docs/rag-retrieval-improvement-survey-cn.md`（6 份分报告在 `logs/research-1..6-*.md`，均附可核实链接，查不到来源的项已显式列出）。

### 调研支持的关键判断

1. **`overview` 的失败主要是 top-k 覆盖预算问题**（2028 切片/141 篇 ≈ 14.4 切片/篇，top-8 覆盖上限 ≈55.6%，与实测 52.8% 吻合）—— 已用实验证实，见下。
2. **超长切片曾被误判为「不可召回」**：按切片全文重新判定后，`long-block` 的 SpanHit 实际为 **100%**（先前的 20% 是度量假象）。同时核实全部 2028 个切片 `index_status=indexed` 且都有向量点，即那个 13,249 字符的超长切片**已被成功嵌入**（`text-embedding-v4` 官方单行上限 8192 token，超限是截断还是报错官方未说明）→ **它不构成检索质量问题，无需为此改造入库侧**。
3. **明确排除的方案**（有依据的"不做"）：
   - 句级重切分 —— 官方评测 "results are roughly the same"，却要重建三套索引；
   - Late Chunking —— 本项目 embedding API 不返回 token 级向量（Jina 官方兼容性清单 + 百炼 API 契约双重证据）；
   - RAPTOR —— 其增益来自书级长文，本项目单篇仅约 3.6K 字符，且 Anthropic 实测文档摘要增益非常有限；
   - 重排分阈值熔断拒答 —— 已被本项目数据证伪（正例最低 0.0009 vs 负例最高 0.8324）；
   - 引入 LangChain/LlamaIndex 组件 —— Java 栈，耦合成本大于收益，只需借鉴思路自研。
4. **参数复核结论**：`overlap=120/800 = 15%` 恰是 NVIDIA 实测最优比例（**不该动**）；真正可疑的是 `minimumSize=40` 字符（≈27–33 token，公开评测最小块都在 100 token 量级），以及 `maximumSize=1600`（≈1,070–1,600 token）正落在观测到性能下滑的区间。

### 配套实验（零索引改动，已完成）

以同一套黄金集做**离线策略实验**（`logs/experiment-strategies.mjs`：只读、不改生产代码、不重建索引）：

**修正后的基线**（判定范围＝切片全文 + `headingPath`）：SpanHit@8 **88.1%**、@20 **90.1%**、DocHit@8 94.1%。最弱仍是 `overview`（72.2%），`long-block` 已达 100%。

| 策略 | SpanHit@8 | 相对基线 |
| --- | --- | --- |
| 基线（现状） | 88.1% | — |
| 邻居 ±1 扩展 | 90.6% | +2.5 |
| 同章节扩展（每命中 ≤4） | 90.6% | +2.5 |
| **邻居 + 同章节（不限预算）** | **91.6%** | **+3.5** |
| 文档配额去重（每文档 ≤2） | 81.2% | −6.9（**放弃**） |
| 参照：k 提到 20 | 90.1% | +2.0 |

**结论**：①检索后扩展**有效、且优于单纯提高 k**（91.6% > 90.1%，因为有些答案切片连 top-20 都进不去但就躺在命中切片隔壁）；②收益集中在 `code`（+6.3）与 `overview`（+5.6），正是要治的两类；`fact` 无收益；③文档配额去重**被数据否掉**；④字符预算扫描显示 **1500 字符是拐点**（90.1%，平均新增 1419 字符 ≈ +47%），推荐作为实现参数（放宽到 2500 收益为零）；⑤残余 8.4% 未命中用例**用答案片段自身检索 20/20 均可达** → 属提问措辞与答案文本的语义错配，非索引/切分问题。

**⚠️ 度量口径更正**：先前报告的 `SpanHit@8 72.3%` / `overview 52.8%` / `long-block 20%` 均受一个缺陷影响 —— 检索接口返回**带连字符 UUID**、切片接口返回**无连字符 ID**，比对失败后回退到 300 字 `contentPreview`。三个脚本（`scripts/rag-eval/run.mjs`、`logs/validate-candidates.mjs`、`logs/experiment-strategies.mjs`）已修复为 ID 归一化 + 全文判定，交付物（`golden.candidates.json`、候选审阅文档）已按修正口径重新生成。

### 据此确定的执行顺序（每步都可被黄金集量化）

- **检索侧（已验证有效，待实现）**：先冻结「扩展后返回单元」的命中口径 → 实现检索后扩展：重排后、截断前，按 `sequence_no ± 1` + 同 `heading_path`（每命中 ≤4 条）补充上下文，**每次查询新增 ≤1500 字符**；
- **入库侧**：`headingPath` 前缀（零 LLM 成本，需重建向量与 BM25）—— 仅在检索侧落地并复测后仍不达标时再做；
- **生成层**：三段式拒答（提示词 → **服务端确定性校验**：chunkId 必须属于本次候选、quote 必须能在原文匹配 → 兜底话术）+ 按 Anthropic/OpenAI 的引用契约输出 `citations[]` + 按 *Lost in the Middle* 的 U 形结论组织上下文顺序。
- **不做**（有依据的否定）：文档配额去重（实测 −6.9pt）、句级重切分、Late Chunking、RAPTOR、重排分阈值熔断、为超长切片专门改造入库侧（实测该类已达 100%）。

## 接口与行为（2026-10-10 自 `project-status-cn.md` 迁入）

契约全文、配置表与设计依据见 `docs/design-11-rag-answer-generation-layer.md`。要点：

- 新端点：`POST /api/v1/admin/rag/answer`（需 `SUPER_ADMIN`）。请求含 `query / scope / topK / rerankEnabled / keywordEnabled / expansion / conversationId`；后两项分别为公开端点与多轮对话预留。
- 返回：`answer` + `citations[]` + `retrieval` 元数据 + `refused / refusalReason / refusalDetail` + `degraded / degradedReason / chatModel`。
- 引用可定位：每条引用带 `chunkId / documentId / documentTitle / headingPath / sourcePath / articleSlug / sequence / quote / quoteVerified`，ID 统一为 **32 位无连字符**，可直接用于 `GET /documents/{documentId}/chunks` 定位原文。
- 拒答与降级：①检索无候选 → **不调用模型**直接拒答；②模型判断资料不足 → 拒答（`model_refused`）；③引用无法核验 → 拒答（`invalid_citation`，`refusalDetail` 给出细分）；④模型不可用或密钥缺失 → **降级返回已检索片段**（`degraded=true`），不是 500。
- 引用校验为**逐条独立**：编号越界或 quote 未逐字核验的那一条被丢弃，只有当没有任何一条可核验时才拒答。
- 上下文默认：总预算 4000 字符、检索后扩展开启（邻居 ±1 + 同章节 ≤4、新增 ≤1500 字符）、每段带 `[n]` 编号与来源，并按 Lost in the Middle 把最强证据置于首尾。

### 订正 Stage 3.2 记录中的一句推论

Stage 3.2 联调记录写过「质量信号可用于拒答：不存在的内容重排分落在 0.0001~0.0021，真实命中 0.80~0.99」。该结论**只在「明显无关」的查询上成立，不能推广为阈值熔断**：扩到 10 条负例（含主题相近但答案缺失的情形，如 Kafka/K8s）后测得正例最低重排分 **0.0008** 与负例最高 **0.8324** 完全重叠，阈值法在本语料上不可用。生成层因此**没有引入任何相似度阈值拒答**，拒答改由「提示词 + 服务端引用校验」两层承担（依据与数据见 `docs/rag-retrieval-improvement-survey-cn.md`）。

## 现场联调记录（2026-10-09，同上迁入）

语料规模：158 文档 / 141 有切片 / **2028** 有效切片 = Qdrant `points_count`。联调脚本 `logs/rag-integration-check.mjs`（**独立复核**：把每条引用重新拉回切片，逐字比对 `quote`、`headingPath`、`sequence`，不采信接口自述）。

### 验收结果（每例 3 轮，抵消模型随机性）

- 正例（5 例 × 3 轮）作答且引用可定位且命中期望文档：**15/15**。
- 负例（10 例 × 3 轮）正确拒答：**28/30**；唯一失败项 `Kafka 的事务消息怎么保证 exactly-once`（2/3 轮作答）属**边界用例**——语料里 Kafka 只有零星提及，模型用真实召回的消息幂等内容作答且引用逐字可核验，是「答案相关性」而非「接地违规」。
- 端到端延迟：中位数 2312ms，最大 15868ms（含模型生成）。
- 负例拒答来源：10 条中 9 条靠模型主动拒答（`model_refused`），服务端引用校验只兜住边界项。

### 模型对比（同一套用例，各 3 轮）

- `Qwen/Qwen2.5-7B-Instruct`：正例 **8/15**。q01 三轮**稳定**答成 MySQL 日志（期望片段就在检索第 1 位）；q02 两轮 answer 里完全没有 citation；q03/q04 各 1 轮单条引用未逐字。
- `Qwen/Qwen3-30B-A3B-Instruct-2507`：正例 **15/15**。
- 结论：正例失败主因是模型指令遵循能力，**不是检索或框架**；默认模型据此改为后者（仍可用 `RAG_CHAT_MODEL` 覆盖）。

### 联调抓到并修复的两处缺陷

1. **扩展片段的 `documentId` 被填成 `documentVersionId`**：独立复核引用时报 `knowledge_document_not_found`（400）。`KnowledgeChunk` 只有 `documentVersionId`，扩展片段没有命中记录，原实现拿版本 id 冒充文档 id。修复：记录扩展片段的来源命中（provenance）并继承其文档信息。
