# Stage 3.3 阶段文档：入库质量修复、评测基线与生成层（Evaluation & RAG Answer Generation）

> 一句话用途：记录 Stage 3.3 修复切片塌缩 Bug、建立 323 条评测基线与开发问答生成层的 Spec 设计目标与实现交付情况。  
> 维护日期：2026-10-17　状态：**已完成**

---

## 1. Spec 设计目标

Stage 3.2 交付后，混合检索链路已经跑通，但在真实笔记统计中发现切分器存在逻辑缺陷，导致产生大量垃圾重复切片。本阶段旨在解决数据切分源头问题，并建立客观评测机制与问答生成能力：

1. **切片器算法缺陷修复**：解决当一行短文本紧跟一条超长文本时，切分器逐字符推进、产生上百个只有一字之差的近重复切片的 Bug。
2. **客观评测基线（让调优看数字）**：编写自动化评测工具，整理并标注 300+ 条真实问题黄金评测集，量化文档召回率与切片命中率，告别“凭感觉调参”。
3. **构建问答生成层（RAG Answer）**：基于检索出的高质量切片组装上下文提示词，调用大语言模型（如通义千问等兼容接口）生成答案。
4. **严格的引用追溯与降级保护**：答案必须带出可靠的引用证据（指明来自哪篇文档、哪个章节），防止模型胡言乱语；当大模型接口不可用或超时时，自动返回已检索到的参考片段，确保服务不直接崩溃报错。

---

## 2. 实现情况

本阶段所有核心目标已全部达成，代码已全部合入 main 主干：

1. **切片缺陷彻底修复**：重写了切片边界回溯算法并补充回归测试；以典型有问题的文档为例，切片数从原本异常的 83 个近重复碎片缩减为正常的 3 个高质量切片；全量重建 158 篇文档索引后，切片长度分布恢复健康。
2. **评测工具与基线落地**：交付了评测脚本（`scripts/rag-eval/run.mjs`）与 323 条黄金问答题库；实测基线显示：文档召回率（DocHit@8）达到 **94.9%**，段落召回率（SpanHit@8）达到 **90.1%**，为后续所有检索优化提供了坚实的衡量标尺。
3. **问答生成层打通**：在 `mindora-rag` 模块中实现了上下文组装器、模型调用适配器与答案生成服务；实测正向提问作答率达到 **15/15**，无关越界问题拒绝作答率达 **28/30**。
4. **模型选型升级**：实测对比发现 7B 小模型在长上下文下容易丢失引用和产生幻觉，项目正式升级为更稳健的 **通义千问 30B 模型（Qwen3-30B-A3B）**，生成质量与引用准确率大幅提高。
5. **服务降级实测通过**：当故意将对话模型地址配置为不可用端点时，接口在 200 状态下明确返回 `degraded=true` 与已检索切片列表，前端可友好展示“模型暂不可用，以下为检索到的参考资料”，系统表现稳健。

## 3. 核心功能与接口一览

- **管理端问答生成接口**：`POST /api/v1/admin/rag/answer`
  - 入参支持用户问题、检索范围（`all` 或 `public`）、候选切片数等。
  - 出参包含模型回答文本、引用列表（含文档标题、章节路径、来源路径、原文摘录等）、是否拒答及降级原因。
- **评测运行工具**：`node scripts/rag-eval/run.mjs --golden=docs/stage-3.3-candidate-questions-cn.md`
  - 自动打靶评测，输出前 8 个切片的覆盖率指标与耗时分布。

---

## 4. 关键规则与已知限制

- **拒答机制的演进**：实测数据证伪了“通过设置重排分数阈值来拒答”的设想（因为有效问题的最低分与无关问题的最高分存在重叠）；因此系统通过 Prompt 规则约束 + 服务端引用有效性复核来协同实现拒答。
- **现行应答契约提示**：本阶段初步实现了带引用的回答生成；在后续 Stage 4 中将进一步升级为“应答三态（有依据/无依据兜底/安全拒答）”与服务端摘录机制（见 `design-11`）。
