# Stage 3 阶段文档：检索底座与向量检索（Retrieval Foundation）

> 一句话用途：记录 Stage 3（Stage 3.1）切片元数据丰富、向量检索链路与后台调试工具的 Spec 设计目标与实现交付情况。  
> 维护日期：2026-10-17　状态：**已完成**

---

## 1. Spec 设计目标

在 Stage 2 完成数据写入和向量化存储的基础上，本阶段旨在打通**检索读取全链路**，并解决前期切片缺乏上下文信息和权限控制缺失的问题：

1. **结构化切片与元数据标记**：让切片具备完整的语义层级（如「主标题 > 二级章节」路径、代码块所属编程语言、段落/列表/表格等块类型），代码块与表格保持整块不被切碎。
2. **向量检索读取链路**：基于 Qdrant 提供语义相似度检索能力，输入自然语言即可召回相关度最高的切片片段。
3. **安全权限硬隔离**：严格按可见性过滤。公开检索只能访问公开已发布切片，管理端可以检索全库；若未明确指定权限范围，默认拒绝执行（防越权）。
4. **后台检索调试可视化**：在后台管理端提供专属的检索调试页面，直观查看输入问题后召回的切片内容、所属章节、相似度得分与重排得分。
5. **重排与服务降级容灾**：支持接入重排（Rerank）模型对初筛结果进行精准再排序；当重排外部服务不可用或欠费时，系统自动平滑降级为按向量相似度排序，不直接报错中断。

---

## 2. 实现情况

本阶段所有核心目标已全部达成，并通过了真实语料的全量验证：

1. **切片元数据模型落地**：通过 Flyway V6 迁移为切片表增加了标题路径、块类型、编程语言等元数据；重写了切片算法，支持常见标题语法，并自动剔除无意义的分隔线噪声切片。
2. **向量点生命周期规范**：向量数据库固定接入虚拟机本地 Qdrant 实例，点 ID 与数据库切片 ID 严格一对一绑定，文档重新索引时自动清理历史旧点，避免点堆积与脏数据。
3. **安全过滤实机通过**：对全量语料（132 篇私有笔记 + 1 篇公开文档）实测：公开范围检索只能召回公开文档切片，私有内容零泄漏；缺少范围参数时严格拒绝。
4. **调试页面与重排降级闭环**：后台检索调试页（`/#/knowledge/retrieval`）上线，输入问题即可返回召回切片、来源文档与所在章节路径；实测当 Rerank 服务异常时自动触发降级提示，恢复后能够正常返回高精度重排分。
5. **全量语料重建验证**：对 133 篇文档完成全量切片与向量入库，数据库有效切片数（1988条）与向量库点数完全一致，端到端检索耗时约百毫秒。

---

## 3. 核心功能与接口一览

- **管理端检索调试接口**：`POST /api/v1/admin/knowledge/retrieval/search`
  - 入参支持查询词、权限范围（`all` 或 `public`）、候选切片数、是否开启重排等。
  - 出参包含命中的切片列表、来源文档、章节路径、向量相似度得分、重排得分及降级状态。
- **文档切片元数据查询**：`GET /api/v1/admin/knowledge/documents/{id}/chunks`
  - 响应新增章节路径、标题层级、块类型与语言元数据。

---

## 4. 关键规则与已知限制

- **正文分离存储**：向量库 payload 仅存储用于过滤的元数据（文档ID、权限、章节路径等），正文仍保存在 MySQL 中，检索召回后再按 ID 批量回查，节约向量库内存开销。
- **超长代码块限制**：超长代码块为保持逻辑完整不会强行切断，可能会略微超出单切片预设的最大字符阈值。
