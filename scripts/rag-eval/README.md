# 检索评测工具（Stage 3.3 / F3）

用来把「检索效果好不好」从**感觉**变成**数字**。包含两件事：

1. **指标评测**：读黄金测试集 → 调检索接口 → 输出 `DocHit@K` / `SpanHit@K` / `MRR`，并给出**熔断拒答阈值**的分离分析；
2. **索引体检**：`--duplicates` 模式扫描全部切片，统计**近重复切片**与长度分布，用于客观判断「切片推进量塌缩」这类缺陷是否真的消失。

---

## 1. 前置条件

- 后端已启动（默认 `http://localhost:8080`），且索引已建立（关键词索引可经 `POST /api/v1/admin/knowledge/keyword-index/rebuild` 重建）。
- 一个 `SUPER_ADMIN` 令牌（管理端接口需要）。三种提供方式任选：
  - `--token <jwt>`
  - `--token-file logs/admin-token.txt`
  - 环境变量 `MINDORA_ADMIN_TOKEN`
  - 或直接用账号登录：`--email <邮箱> --password <密码>`（脚本调用 `/api/v1/auth/login`）
- **凭据不要写进仓库**：脚本不落盘任何令牌，`logs/` 已在 `.gitignore` 中。

---

## 2. 怎么标注黄金集

**核心原则：先写问题，再标答案。** 不要拿切片反推问题——那会让评测被切片边界绑架，测不出真实使用场景。

### 2.0 提问视角：必须分清「通用式」与「指代式」

公开的知识库面向的是**不知道哪篇文档里写了什么**的访客。评测题必须按这个场景写，否则指标会虚高（问题本身泄漏了答案位置）。

| 视角 | 说明 | 能否作为主口径 |
| --- | --- | --- |
| **通用式（generic）** | 只用公开可见的主题词：技术名、项目名、论文缩写、通用概念 | ✅ **必须占绝大多数** |
| 指代式（pointed） | 含只有作者才知道的细节：文件名、具体数值、内部指代、"我之前那个" | ❌ 仅可少量保留作对照 |

**✅ 通用式示例**

- 「Redis 的常见缓存问题和解决方案有哪些？」
- 「DDIM 的核心思想和改进是什么？」
- 「家政项目里的核心链路是怎样的？」
- 「Transformer 的三层注意力分别是什么？」

**❌ 指代式（不要作为主口径）**

- 具体数值：`PSNR 是多少`、`T=15 时…`、`best_step=35000`
- 文件名 / 路径 / 脚本名：`prior_mask.py 在哪`
- 章节或表格的具体措辞：`那个 XX 消融大表里…`
- 只属于作者的指代：`我给自己这套方法起的名字`、`我在 X 上踩的坑`
- 直接复制原文片段当作问题

**判断标准**：一个从没见过这个知识库的人，能否在不看文档的情况下问出这句话？

> **例外**：公开的错误信息 / API 名 / 配置项**可以**出现在问题里（例如「Redis 报 `attempt to compare nil with number` 怎么解决」「`@EnableAutoConfiguration` 的作用是什么」）——它们本身就是公开可检索的标识符，不泄漏「答案在哪个文档」。

`run.mjs` 与候选校验脚本会用启发式规则（具体数值 / 参数赋值 / 命令行参数 / 文件名 / 作者指代 / 超长引用）自动标记指代式提问，并**分别统计两种视角的 `DocHit` 与 `SpanHit`**，用于判断问题集是否偏离公开使用场景。

### 2.1 写 30~50 个真实问题

从你**最近真的想查过**的内容里出，尽量覆盖这些题型（`type` 字段）：

| type | 说明 | 为什么需要 |
| --- | --- | --- |
| `fact` | 单一事实/配置/结论 | 基础命中能力 |
| `code` | 报错、API 名、代码标识符 | 关键词召回的主场 |
| `cross-section` | 答案分散在同一文档的不同章节 | 验证标题上下文缺失的影响（语料中约 19.8% 切片无标题） |
| `vague` | 口语化、用词与你笔记不一致 | 验证语义召回与混合检索 |
| `multi-doc` | 答案需要跨文档 | 验证融合与重排的多样性 |
| `long-block` | 答案在超长代码块内 | 已知限制：最长切片 13249 字符 |
| `no-answer` | **知识库确实没有**的答案 | 决定熔断/拒答阈值，占比建议 10~20% |

### 2.2 标答案锚点（关键：不要纠结切片边界）

你的笔记是随手记的，切片边界不清晰，所以锚点分两级即可：

| 级别 | 字段 | 说明 | 是否必填 |
| --- | --- | --- | --- |
| **L1 文档级** | `expectedDocs` | 答案所在文档的**标题**（或 documentId） | ✅ 必填 |
| **L2 片段级** | `keySpans` | 从原文复制 **10~30 字**的唯一片段，可多个 | ✅ 强烈建议 |

> 脚本会按返回的 `chunkId` **拉取切片全文**再做子串匹配，因此不受接口 `contentPreview` 300 字截断的影响。

一题允许标多个文档与多个片段（你的笔记经常一处记录、多处相关）。**不需要**标切片 id。

### 2.3 规模与节奏

先做 30 条跑通（约 2~4 小时），确认指标口径无误后再扩到 50~100 条。**每次改动检索参数前先跑一遍基线**，改完再跑对比。

## 3. 运行

```bash
# 指标评测（默认读 scripts/rag-eval/golden.example.json）
node scripts/rag-eval/run.mjs --token-file logs/admin-token.txt

# 指定黄金集与返回条数，并导出明细
node scripts/rag-eval/run.mjs --token-file logs/admin-token.txt \
  --golden scripts/rag-eval/golden.mine.json --top-k 8 --json logs/eval-baseline.json

# 只用向量单路（做 A/B）
node scripts/rag-eval/run.mjs --token-file logs/admin-token.txt --golden scripts/rag-eval/golden.mine.json

# 索引体检：近重复切片 + 长度分布
node scripts/rag-eval/run.mjs --token-file logs/admin-token.txt --duplicates
```

可用参数：`--base`、`--top-k`、`--scope`、`--golden`、`--json`、`--duplicates`、`--help`。
单条用例也可用 `scope` / `keywordEnabled` 覆盖（便于针对性 A/B）。

## 4. 指标定义

| 指标 | 定义 | 回答什么问题 |
| --- | --- | --- |
| `DocHit@K` | 前 K 条里是否出现 `expectedDocs` 中的文档 | 检索有没有找到对的地方 |
| `SpanHit@K` | 前 K 条里是否有切片的**正文或 `headingPath`** 包含某个 `keySpan` | 找到的是不是**答案所在的那一块** |
| `MRR` | 首个命中（文档或片段）排名的倒数均值 | 相关结果排得够不够靠前 |

之所以同时看两个命中率：`DocHit` 会**高估**（碎片也算命中同一文档），`SpanHit` 更严格，两者的差距本身就是「切片质量」的度量。

**阈值分离分析**：脚本会输出

- 正例中**命中切片的最低重排分**
- 负例中**最高重排分**

两者只要不重叠，就可以取中间值作为**熔断拒答阈值**（低于该分则不调用大模型直接回答"知识库没有记录"）。这决定了生成层的成本与幻觉抑制强度。

## 5. 用这套工具回答两个具体问题

### 5.1 「上一轮的切片推进塌缩修复是否必要？」

- **客观指标**：`--duplicates` 的近重复切片对数。修复前该缺陷会产出「逐字符位移」的近重复切片（实测某文档 1857 字符 → 83 个切片，字符膨胀 6.22x）；修复后应为 **0**。
- **检索指标**：在黄金集里加入**答案落在曾经受影响文档**的用例（如「个人知识库开发记录」「初稿优化」），比较这些用例的 `SpanHit@K`。修复前这些文档的近重复切片会占满 top-K 名额，把真正相关的结果挤出去。
- **判定**：若这两项都显示无差异，则应记录为「该修复的价值主要在正确性与可复现性（切片数不再依赖换行位置的偶然性、不再产出重复内容），而非当前语料的检索指标」，并据此决定是否继续保留（建议保留：它同时消除了未来新笔记再次触发的风险）。

### 5.2 「是否应该改掉『块类型交替即 flush』？」

- 在黄金集里加入**碎片题**：答案落在「问题（列表）/回答（段落）交替」的短块中（当前语料剩余 614 个 <50 字符切片，paragraph 405 + list 184）。
- 同时**人工判断「片段自足性」**：命中的切片单独看是否足以回答问题。实测出现过反例——41/68 字符的碎片 rerank 高达 0.935/0.951，因为碎片本身就精确包含答案。
- **判定**：如果碎片题 `SpanHit` 高但自足性低，说明**检索没问题、生成会缺上下文**，此时应保留检索行为、改为在生成层按需扩展上下文（例如命中后回取同章节相邻切片）；如果碎片题 `SpanHit` 本身就低，才值得改 flush 策略。

---

## 6. 注意事项

- 脚本是只读的：只调用 GET 与检索 POST，不写库、不改索引（`--duplicates` 也只读）。
- 指标模式会为每个命中文档拉一次切片列表并缓存，30~50 条用例的额外请求量很小。
- 每次**改动切分或索引**后，指标都不可与旧基线直接比较——必须重新全量重建索引后再跑基线。
